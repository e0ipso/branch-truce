# Journey acceptance checks

`JourneyAcceptanceTests.cpp` checks the observable acceptance examples in `PRD.md` through the real application. Each journey creates a disposable Git repository, stops a real merge or rebase on conflicts, opens it with `SessionLoader::openRepository` and loads the real `BranchTruce` `Main` scene. The test then drives that scene with mouse clicks and key events and compares what it shows with the repository and the Git index.

## Running it

From a configured desktop build:

```sh
cmake --build build/desktop --parallel 2 --target branch_truce_journey_acceptance_tests
ctest --test-dir build/desktop -L acceptance --output-on-failure
```

Three CTest entries run the journeys, each with the label `acceptance`: `acceptance.journeys-review` (the six journeys on the panes, choices, editing, search and Save), `acceptance.journeys-handoff` (the handoff, startup recovery and mergetool journeys) and `acceptance.journeys-window` (window fit, first undecided region, hand edits, line choices inside one conflict and the close guard). Each passes its group name as the only argument, and the binary with no argument runs every journey. Any other argument exits with status 2. CTest sets `QT_QPA_PLATFORM=offscreen` and `QT_QUICK_BACKEND=software`, and for `acceptance.journeys-window` also `QT_QUICK_CONTROLS_STYLE=org.kde.desktop`, the style the app selects at startup. To run the binary directly, set those variables yourself. It exits with status 2 on any other platform plugin. Each entry takes 15 to 27 seconds alone on the development host, up to 39 seconds with all three running together, and has a CTest timeout of 120 seconds; the window journeys took 31 to 38 seconds under `org.kde.desktop`. When a journey is added, put it in the group with the most headroom and keep the timings in `tests/CMakeLists.txt` current.

The process sets up its own environment before Qt starts. It uses a private `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME` and an owner-only `XDG_RUNTIME_DIR` under one temporary directory, so the recovery store and the mergetool socket never touch the real ones. `PATH` starts with a `git` wrapper that logs every argument the app passes and refuses `fetch`, `pull`, `push`, `clone`, `ls-remote`, `remote`, `submodule` and `credential`. Each fixture repository has an unreachable `origin` remote, and the HTTP proxy variables point at a closed local port. The fixtures call `/usr/bin/git` directly, so the log holds only the app's commands.

`tests/fixtures/QuickScene.h` holds the offscreen helpers that this suite shares with `tests/app/ComparisonViewTests.cpp`. They are `settle`, `visualItem`, `accessibleName`, `namedButton`, `popupRoot`, `waitForStable`, `waitForLayout`, `clickItem` and the wrap and whitespace probes.

## Locating controls

Tests find a control by its `objectName`, never by the text on it, so a new label or an icon-only button does not break them. Give every control a test clicks an `objectName`. A delegate that repeats per row puts the row's ID in it: the scoped choices are `choiceAccept-<id>`, `choiceIgnore-<id>`, `choiceResolve-<id>`, `choicePreviewLeftFirst-<id>` and `choicePreviewRightFirst-<id>`. They live in the source pane gutters under `scopedChoices`. Accept and Ignore of the scope that owns a gutter row are buttons on the row; the other choices, including those of a line choice on a section's first line, are entries of the row's menu `choiceMore-<owner id>`, and `clickChoice` opens it first.

A button the scene cannot name, such as a dialog's standard OK, Cancel or Apply button or a combo box entry, is found by its accessible name instead. `namedButton` tries the `objectName` first and the accessible name second. `accessibleName` returns `Accessible.name`, or else the button's or label's text, which is the name Qt gives assistive technology when none is set. `clickDialogButton` searches the dialog's whole item tree from `popupRoot`, so a footer that is not a plain `DialogButtonBox` works too.

Assert state through properties, not labels. The file list toggle exposes `checked` and keeps the accessible name "Show file list" while its text changes. The 1280x720 journey requires a non-empty accessible name on every control in `mainControls`.

Regression journeys outside the PRD table:

- `TRUCE-0087 a resolved mergetool handoff drops the waiting text` runs real `git mergetool` on one of two paths. Git starts this test binary with `--mergetool`, and `main()` then runs the real launcher code against the session in the test process. While Git waits, the path it has not launched says "Waiting for Git to launch this path. It is not resolved." After Mark resolved, Git exits 0 and stages the result. The resolved file then shows no waiting text, and neither does the same file after a later edit leaves the earlier result staged. The other path still shows the text.
- `TRUCE-0082 clicking the launched path again after Git attached` selects one of two paths and runs real `git mergetool` on it. Once Git waits on that path, a click on the other file's row shows "Waiting for Git to launch this path" and hides Leave unresolved. A second click on the launched path's row shows the waiting text "Git is waiting on this path" and an enabled Leave unresolved again. Clicking Leave unresolved ends `git mergetool` with a nonzero status, restores the launched file's bytes and leaves both paths unmerged.
- `TRUCE-0088 a 1280x720 logical screen fits the window` opens a merge with four files and the outside-app warning, then resizes the window to 1280x720 and 960x540, the logical sizes of a 1920x1080 screen at 150% and 200%. Every named control and all three text panes must lie inside the window once enclosing views have scrolled to them, and each pane must be at least eight lines high. At 960x540 the mouse wheel over a label may scroll the page only when the page is taller than the window, which depends on the fonts: with DejaVu Sans 9 pt, as in the CI images, it fits. The source choices start shown in the source pane gutters and take no height: from 1500x1040 down to 960x540 each pane keeps eight lines with them, and hiding them leaves every text pane as high as it was. At 1600x1200 the page must not scroll. These are logical sizes in the offscreen platform, not a scaled output; `docs/platform-validation.md` records the scaled container runs.
- `TRUCE-0126 a choice clears hand edits on a line deleted in the editor and on text an edit left unchanged` starts from a result the user set to the left side, where one section changes two lines. Deleting one of them in the editor leaves its region marked as hand-edited with no result range. Accepting the section previews the replacement of the hand edit, puts the line back and clears every mark, and Undo and Redo walk both states. Typing a character and deleting it marks a region without changing the text. Choosing Preview whole file from Left from the Source choices menu again keeps the text and decisions, clears the mark, and is one undo step.
- `TRUCE-0171 lines from both sides of one multi-line conflict keep their text, decisions and undo` covers PRD.md:49. It starts from a result the user set to the common version, where both sides change the same three lines. Every left and right line inside that conflict can be chosen, and each one's result range is the result line at its own index. Accepting the middle left line and then the last right line previews and replaces only those launch lines. Ignoring the first left line keeps the text. Undo walks back through the text and decisions together, and redo replays them.
- `TRUCE-0116 closing with input recovery could not keep asks to retry, and cancel keeps the window open` holds the recovery journal lock from the test, so the recovery commit for a typed character fails and the input stays pending. Closing the window then opens the `recoveryCloseDialog` prompt instead of the handoff. Cancel keeps the window open, and Retry while the lock is still held keeps the input pending and the window open. Once the lock is released, Retry keeps the input and the close goes on to the handoff. After Leave, the repository is unchanged and a new window restores the retried input.

Every journey also runs `checkOffline`. It asserts that the guard saw no network command, that the app ran local `rev-parse` and `cat-file`, and that no visible text in the scene mentions signing in, logging in, registering, an account, a subscription, a payment or a license key.

PRD examples 4 (whole-file and bulk choices), 11 (crash recovery) and 15 (merge-tool cancellation) are outside this ticket. The suite does not cover them.

## Environment-dependent gaps

- The suite uses the offscreen platform with the software Quick backend. It does not check a real Wayland or X11 session, KDE themes, scaling, input methods on a physical keyboard, accessibility metadata seen by assistive technology, or the colours of focus and progress indicators. TECH_SPEC.md:227 leaves those to packaged-application checks on the target desktops.
- A `git` wrapper on `PATH` plus proxy variables stands in for having no connection. No network namespace is involved, so a direct socket opened by Qt or a library would not be caught.
- Scrolling inside the handoff dialog and the scoped-choice list sets the view position directly instead of sending wheel events. The search scope is changed with real clicks on the combo box and its popup.
- The write-failure journey makes a directory read-only. Root ignores directory permissions, so that step fails when the suite runs as root.
- Apart from the recovery commit that the close guard journey makes fail by holding the journal lock, a failed draft save, a file that cannot open, and leave refused because of pending input or a running resolution need fault injection, so this suite does not provoke them. They are covered in `tests/app`: `TRUCE-0015 Save and discard controls keep the app baseline and retry a failed Save`, `TRUCE-0053 failed placeholder recovery keeps captured files visible blocks editing and retries the captured state`, and `TRUCE-0074 leave refuses unrecovered input and a running resolution and finish waits for a clean handoff`.
- With Git's raw conflict output as the result, Accept and Resolve using this side change only decisions, because both sides' lines are already in the result. Known conflict markers then block Mark resolved. The choice journey starts from a result that the user had set to the common version before launch, so the text changes it checks can be seen.
