## Which language and binding routes fit a Linux and KDE desktop application?

### Takeaway

Recommend a Qt-independent Rust domain engine, a small CXX-Qt QObject/model layer, and a Qt Quick/Kirigami UI as the first route to evaluate. Make the custom editor a decision gate before committing to Qt Quick. Retain a Rust engine with a C++ Qt Widgets frontend as an explicit fallback if editor integration proves more maintainable there. This is a recommendation, not an adopted stack.

### Cited Findings

#### Requirements and the distribution baseline

- The required product is an offline Linux merge/rebase tool with two read-only sources around an editable center, earlier context on demand, individual-line and region choices, synchronized correspondence, word-level highlighting, text-plus-decision undo, separate save and resolution, all current conflicts in a session, and recovery. The PRD makes no file-size or response-time promise. [PRD requirements](../../PRD.md).
- Future platforms should use loosely coupled, idiomatic desktop UI kits. Shared UI code is not a requirement. [Repository architecture convention](../../.ai/kenkeep/nodes/practice-design-desktop-apps-around-screens-and-components.md).

#### Modern C++ with Qt and KDE Frameworks

- Qt 6 requires at least **C++17** and documents C++20 integration. KDE's application compiler settings default to **C++20** when `KDE_COMPILERSETTINGS_LEVEL >= 6.13`; older settings levels differ. C++20 is therefore a supported practical choice for any necessary adapter, not an assertion that Qt requires it. [Qt C++20 overview](https://doc.qt.io/qt-6.8/cpp20-overview.html), [KDECompilerSettings](https://api.kde.org/ecm/kde-module/KDECompilerSettings.html).
- Qt documents CMake targets and automatic `moc` integration. KDE supplies install/compiler conventions through Extra CMake Modules. An application should use `KDECompilerSettings`, not copy `KDEFrameworkCompilerSettings` from Frameworks source trees; the latter explicitly warns against use outside Frameworks. [Qt CMake guide](https://doc.qt.io/qt-6.8/cmake-get-started.html), [Frameworks-only warning](https://api.kde.org/ecm/kde-module/KDEFrameworkCompilerSettings.html).
- Direct C++ access avoids the need for a language binding for each KDE class. A concrete editor example is `KTextEditor::View`, a QWidget with KXMLGUIClient integration and documented coordinates, scrolling, annotations, and inline notes. That API evidence does not establish complete merge-editor suitability. [KTextEditor view API](https://api.kde.org/ktexteditor-view.html).

#### Python: distinguish Qt for Python from KDE Frameworks bindings

- **PySide6 is Qt for Python.** It exposes Qt Widgets and Qt Quick; `QPlainTextEdit` has a Python API. This confirms Python can build an ordinary Qt desktop editor without PyKF6. It says nothing about access to every KDE Framework. [Qt for Python introduction](https://doc.qt.io/qtforpython-6.8/index.html), [Python QPlainTextEdit API](https://doc.qt.io/qtforpython-6.8/PySide6/QtWidgets/QPlainTextEdit.html).
- KDE documents Python bindings for **some** Frameworks, listing **KCoreAddons, KGuiAddons, KWidgetsAddons, KStatusNotifierItem, KNotifications, KUnitConversion, and KXmlGui**, including example classes. It warns that bindings are new, distribution coverage varies, and their Qt version must match PySide's. [KDE Python bindings guide](https://develop.kde.org/docs/getting-started/python/python-bindings/).
- The guide's linked binding work is merged for all seven listed libraries. Upstream MR status was checked through KDE's GitLab API, not inferred from documentation alone. [KCoreAddons MR 467](https://invent.kde.org/frameworks/kcoreaddons/-/merge_requests/467), [KGuiAddons MR 149](https://invent.kde.org/frameworks/kguiaddons/-/merge_requests/149), [KWidgetsAddons MR 258](https://invent.kde.org/frameworks/kwidgetsaddons/-/merge_requests/258), [KNotifications MR 157](https://invent.kde.org/frameworks/knotifications/-/merge_requests/157), [KStatusNotifierItem MR 26](https://invent.kde.org/frameworks/kstatusnotifieritem/-/merge_requests/26), [KUnitConversion MR 48](https://invent.kde.org/frameworks/kunitconversion/-/merge_requests/48), [KXmlGui MR 258](https://invent.kde.org/frameworks/kxmlgui/-/merge_requests/258).

An unchecked entry establishes that coverage is unconfirmed in this tracker, not proof that no downstream or experimental binding exists. [Python support tracker](https://invent.kde.org/teams/goals/streamlined-application-development-experience/-/issues/9), [machine-readable issue description](https://invent.kde.org/api/v4/projects/teams%2Fgoals%2Fstreamlined-application-development-experience/issues/9).

- KDE's generator uses **Shiboken**; `ECMGeneratePythonBindings` is explicitly experimental/internal. Framework coverage and individual class/method coverage need separate checking. The documented generator belongs to the Shiboken/PySide approach; the guide's references to PyQt do not establish interchangeable Python wrapper objects. [Generator documentation](https://api.kde.org/ecm/module/ECMGeneratePythonBindings.html).

#### Rust with CXX-Qt, qmetaobject-rs, or a thin C++ adapter

- **CXX-Qt** uses CXX and code generation to bridge Rust and Qt, including Rust-implemented QObjects exposed to QML. It deliberately bridges idioms rather than providing a complete one-to-one Rust wrapper for Qt. Missing Qt integration can be written in C++ and connected through CXX. [CXX-Qt introduction](https://kdab.github.io/cxx-qt/book/), [project's published crate description](https://docs.rs/crate/cxx-qt/0.10.0).
- The latest CXX-Qt release observed was **0.10.0**, published **2026-08-24**, confirmed by its release API and tagged changelog. The tagged workspace declares Rust **1.85.0** as its minimum. A KDE setup example still uses 0.8.1, so tutorial versions are not release discovery. [Release](https://github.com/KDAB/cxx-qt/releases/tag/v0.10.0), [latest-release API](https://api.github.com/repos/KDAB/cxx-qt/releases/latest), [tagged workspace](https://github.com/KDAB/cxx-qt/blob/v0.10.0/Cargo.toml), [KDE example](https://develop.kde.org/docs/getting-started/kirigami/setup-rust/).
- KDE documents Rust + Kirigami through CXX-Qt. Its Rust Frameworks guide points to `cxx-kde-frameworks`, demonstrates KCrash, KCoreAddons and KI18n, and warns that these bindings may change with future Qt Bridges work. This establishes a route and an integration risk, not comprehensive KF coverage or adoption levels. [Rust with Kirigami](https://develop.kde.org/docs/getting-started/rust/), [Rust Frameworks guide](https://develop.kde.org/docs/getting-started/rust/rust-bindings/).
- **qmetaobject-rs** generates metaobjects and exposes QObject/QML types. Its own README says its focus is QML, not QWidget or broad non-graphical Qt APIs, and says it is **passively maintained** because the author's focus shifted to Slint. This is a direct maintenance signal. [Maintainer README](https://github.com/woboq/qmetaobject-rs).
- Do not label qmetaobject-rs categorically Qt5-only. Its source has Qt6-specific metaobject code, and its Qt discovery code tries `qmake6`. That shows Qt6 work exists; it does not certify the exact Qt 6.10.2/KF6 editor combination. [Metaobject source](https://github.com/woboq/qmetaobject-rs/blob/master/qmetaobject/src/lib.rs), [Qt discovery source](https://github.com/woboq/qmetaobject-rs/blob/master/qttypes/build.rs).
- A **Rust engine + C++ Qt adapter** does not require making the engine QObject-aware. CXX supports an explicit shared boundary and standard ownership types such as Rust Box and C++ unique_ptr. CXX-Qt becomes useful when Rust itself implements Qt-facing QObjects/models; plain CXX is sufficient when C++ owns that entire adapter. [CXX design](https://cxx.rs/), [Rust Box binding](https://cxx.rs/binding/box.html).

### Inferences

- **Recommended binding choice:** prefer CXX-Qt over qmetaobject-rs for Rust-owned Qt-facing state. Its explicit Qt/C++ bridge and maintained release path fit planned custom adapters; qmetaobject's stated QML-only focus and passive maintenance add avoidable risk here. This is a project-fit judgment, not a measured speed or popularity ranking. [CXX-Qt model](https://kdab.github.io/cxx-qt/book/), [qmetaobject maintainer statement](https://github.com/woboq/qmetaobject-rs).
- Keep merge decisions, correspondence data, history semantics, recovery records and Git-workflow state in ordinary Rust modules. Expose commands and view data through a narrow adapter. That gives future idiomatic frontends a possible shared engine without promising shared Qt UI. [CXX boundary design](https://cxx.rs/), [local portability convention](../../.ai/kenkeep/nodes/practice-design-desktop-apps-around-screens-and-components.md).
- Python remains a credible Qt frontend option, but it is less aligned with this developer's Rust preference. Choosing Python in addition to Rust would need a concrete productivity reason that outweighs another integration layer. Its inability to guarantee desired KF bindings should be evaluated per feature, not used as a blanket rejection. [Qt/Python route](https://doc.qt.io/qtforpython-6.8/PySide6/QtWidgets/QPlainTextEdit.html), [KDE coverage](https://develop.kde.org/docs/getting-started/python/python-bindings/).

### Gaps

- User's actual TUXEDO edition/base and installed library revisions are unknown. July vendor announcements cannot establish the October state of that machine. UI research owns the detailed distro matrix; the baseline above is sufficient to avoid designing against upstream Qt 6.12 by accident.
- PyKF6 per-class coverage and binary packages on stock Kubuntu 26.04 were not validated. Merged upstream bindings do not prove a distro builds or ships them. KI18n's tracker/MR contradiction remains unresolved.
- No evidence was collected that justifies ranking these choices by popularity, startup time, memory, diff throughput, or AI-generated code quality.

## What do editor integration, ownership, background work and packaging require?

### Takeaway

The largest open engineering choice is the editor, rather than whether Rust can call Qt. Keep GUI objects and Qt models on their owning thread, compute diffs from immutable snapshots, and apply revision-checked results. Distribution choices must account for native Qt/KF libraries even when most application logic is Rust or Python.

### Cited Findings

#### Qt Quick and widget editors are different commitments

- Qt Quick `TextEdit` provides editable plain text, read-only mode, wrapping, insertion/removal, undo/redo, and coordinate/position methods. Its documentation says it does **not itself implement scrolling or cursor-following**. Cursor positions count UTF-16 units, not necessarily graphemes. These are building blocks, not a documented three-pane merge editor. [Qt 6.10 TextEdit](https://doc.qt.io/qt-6.10/qml-qtquick-textedit.html).
- `QQuickTextDocument` exposes the underlying QTextDocument for operations such as extra formatting with QSyntaxHighlighter. Since Qt 6.7 it can accept another document, with ownership retained by the caller. Several file/status properties are still marked preliminary in Qt 6.10. [QQuickTextDocument](https://doc.qt.io/qt-6.10/qquicktextdocument.html).
- Qt Widgets `QPlainTextEdit` documents read-only text, search, wrapping, extra selections for temporary region highlighting, visible-block geometry, and `updateRequest` for gutters or related widgets. `setPlainText` clears its undo/redo history. These APIs make it a concrete candidate, but no cited API guarantees aligned correspondence across three differently edited documents. [QPlainTextEdit](https://doc.qt.io/qt-6.8/qplaintextedit.html).
- `KTextEditor::View` supplies a QWidget-based editor with document separation, annotations and inline notes. Its built-in actions can be integrated through KXMLGUI. This confirms a widget route; the source does not present KTextEditor as a drop-in Qt Quick item. [KTextEditor::View](https://api.kde.org/ktexteditor-view.html).
- `QQuickWidget` embeds a **Qt Quick UI inside a QWidget application**. It does not establish the inverse embedding of QPlainTextEdit/KTextEditor in a QML scene. Qt documents additional rendering and stacking considerations for hybrid UIs. [QQuickWidget](https://doc.qt.io/qt-6.10/qquickwidget.html).
- `QUndoStack` provides command grouping and a saved/clean position. It does not define Branch Truce's decision history, review state or Git resolution. [Qt undo stack](https://doc.qt.io/qt-6.8/qundostack.html), [required undo and status semantics](../../PRD.md).

#### Event loops, FFI and cancellation

- QWidget subclasses must be used on the main thread. QObjects have thread affinity; a queued signal invokes the receiver on its thread through its event loop. [Threads and QObjects](https://doc.qt.io/qt-6.8/threads-qobject.html).
- QAbstractItemModel is not thread-safe. Worker threads may compute data, but model API updates belong on the model's owning thread, normally the GUI thread. [Model thread-safety contract](https://doc.qt.io/qt-6.8/qabstractitemmodel.html#thread-safety).
- CXX-Qt-generated QObjects are neither `Send` nor `Sync`. Its `Threading` trait provides a `CxxQtThread` handle to queue work onto the QObject's thread. Queueing can fail after destruction; checking `is_destroyed` first does not remove that race. [Threading API](https://docs.rs/cxx-qt/0.10.0/cxx_qt/trait.Threading.html), [queue/lifetime contract](https://docs.rs/cxx-qt/0.10.0/cxx_qt/struct.CxxQtThread.html).
- qmetaobject also has ownership constraints: exposed QObjects must be pinned and use RefCell for reentrancy; `queued_callback` returns work to the Qt thread. A Rust binding does not eliminate Qt's lifecycle rules. [qmetaobject API](https://docs.rs/qmetaobject/0.2.10/qmetaobject/).
- QtConcurrent has distinct basic and promise-based `run` modes. The promise mode supports cooperative cancellation through checks such as `isCanceled`; do not assume cancelling a future forcibly interrupts arbitrary diff code. [Qt concurrent modes](https://doc.qt.io/qt-6.8/qtconcurrentrun.html).
- Standard GIL-enabled CPython permits only one thread to execute Python bytecode at a time. Processes are an option for CPU parallelism. Free-threaded Python exists, but extensions can re-enable the GIL. This is a scheduling constraint, not evidence that a Python UI will be too slow. [Python threading](https://docs.python.org/3.14/library/threading.html), [free-threading extension caveat](https://docs.python.org/3/howto/free-threading-python.html).
- Shiboken tracks Python/C++ ownership and invalidates wrappers when C++ destroys the underlying objects; QObject parent-child lifetime rules still apply. [Shiboken ownership documentation](https://doc.qt.io/qtforpython-6/shiboken2/typesystem_ownership.html).
- CXX maps fallible `Result` calls to C++ exceptions and aborts if a panic crosses an extern Rust function. KDECompilerSettings disables exceptions by default but provides a per-target opt-in. An adapter must deliberately choose exception-enabled translation or explicit error/status values. [CXX error contract](https://cxx.rs/binding/result.html), [KDE compiler defaults](https://api.kde.org/ecm/kde-module/KDECompilerSettings.html).

#### Build and distribution consequences

- CXX-Qt supports Cargo-first or CMake integration; both use `build.rs`. Its build documentation distinguishes static QML plugins from dynamic QML modules, with dynamic generation supported through CMake. Cargo does not remove the native Qt build step. [CXX-Qt build systems](https://kdab.github.io/cxx-qt/book/concepts/build_systems.html).
- Qt deployment includes appropriate runtime libraries and platform/plugins, with compiler and system-library compatibility to consider. A Rust executable linked to Qt/KF remains subject to those native dependencies. [Qt Linux deployment](https://doc.qt.io/qt-6.8/linux-deployment.html).
- PySide wheels include Qt binaries; Qt's guide specifically notes that system style plugins do not affect that installation. Combined with KDE's same-Qt-version requirement, mixing a pip Qt runtime with distribution-built Frameworks bindings is an integration question, not an automatic KDE-native packaging solution. [Qt/Python wheel behavior](https://doc.qt.io/qtforpython-6.8/gettingstarted.html), [KDE binding requirement](https://develop.kde.org/docs/getting-started/python/python-bindings/).
- `pyside6-deploy` wraps Nuitka and links libpython. Current documentation says the default changed to a standalone directory in 6.12 and supports explicit one-file mode. This does not certify collection of arbitrary KF extension libraries. [Deployment tool](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html).
- KDE documents a Python Flatpak using `org.kde.Platform`, `org.kde.Sdk`, and a PySide BaseApp. The example's runtime numbers are examples, not a checked current runtime selection. [KDE Python Flatpak workflow](https://develop.kde.org/docs/getting-started/python/python-flatpak/).
- Flatpak filesystem access is sandboxed and host paths may require permission or portal access. That directly affects a tool launched into arbitrary repositories and temporary files. [Flatpak permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html).

### Inferences

- **Qt Quick editor gate:** evaluate a three-pane editor on Qt 6.10.2 before adopting QML for the full workspace. It must demonstrate wrapped correspondence, line/region controls, non-destructive word highlighting and whitespace display, selection/copy, IME, Unicode offset conversion, and undo for both manual edits and decisions. Generic TextEdit availability does not answer those questions. [TextEdit mechanisms](https://doc.qt.io/qt-6.10/qml-qtquick-textedit.html), [PRD acceptance examples](../../PRD.md).
- A QML frontend can use a **small C++ document/formatting adapter** when public QTextDocument APIs are missing from Rust wrappers. Keep it limited to editor/document integration. Whether that adapter stays small is unproven; synchronized virtual gaps and wrapping may require more than highlighting. [QQuickTextDocument access](https://doc.qt.io/qt-6.10/qquicktextdocument.html), [CXX-Qt bridge scope](https://kdab.github.io/cxx-qt/book/).
- If QPlainTextEdit or KTextEditor proves the better editor, use an honest Qt Widgets frontend around the Rust engine. Its view/event code may be substantial, so describe it as a C++ UI with Rust backend rather than promising an almost-all-Rust GUI. A mixed QWidget/QML shell is possible in the documented direction, but adds another integration contract. [Widget editor](https://api.kde.org/ktexteditor-view.html), [QQuickWidget direction](https://doc.qt.io/qt-6.10/qquickwidget.html).
- Give one component authority over history. A proposed Rust command history should record text deltas and decision changes atomically; editor-local text history must be coordinated or bypassed through a documented command adapter. Avoid two independent Ctrl+Z histories. Keep saved-content identity separate from decision-only edits, reviewed revisions and actual Git state. [Qt command history](https://doc.qt.io/qt-6.8/qundostack.html), [local explicit-choice rule](../../.ai/kenkeep/nodes/practice-make-conflict-choices-explicit-and-reversible.md), [saving rule](../../.ai/kenkeep/nodes/practice-separate-save-from-mark-resolved.md).
- Run diff/correspondence work on immutable text snapshots in bounded workers. Attach file identity and result revision to each request; discard stale completions on the Qt thread. Cancellation needs a token checked inside the selected algorithm, plus stale-result rejection if the library cannot interrupt promptly. Queue failure during view destruction should be handled as expected shutdown. [Qt model restriction](https://doc.qt.io/qt-6.8/qabstractitemmodel.html#thread-safety), [CXX-Qt queue](https://docs.rs/cxx-qt/0.10.0/cxx_qt/struct.CxxQtThread.html), [cooperative cancellation example](https://doc.qt.io/qt-6.8/qtconcurrentrun.html).
- Let Qt own the UI event loop. Begin with ordinary Rust worker threads rather than adding a second general async runtime without a requirement. Do not block the Qt thread waiting for a worker; compute outside the GUI and return value data. [CXX-Qt documented worker example](https://docs.rs/cxx-qt/0.10.0/cxx_qt/trait.Threading.html).
- Recovery should persist Rust-owned edits and unresolved choices, distinct from the working-tree save and Git resolution steps. Do not serialize QObject pointers or infer successful resolution from a UI flag. Persistence format and durability strategy remain decisions. [Recovery rule](../../.ai/kenkeep/nodes/practice-recover-unfinished-work-without-changing-its-status.md), [failure rule](../../.ai/kenkeep/nodes/practice-keep-failed-work-outstanding.md).
- For a solo/AI-maintained mixed project, favor one documented top-level build command: CMake + ECM invoking Cargo when native adapters/KF dependencies are present. Cargo-first remains reasonable for a mostly QML/CXX-Qt application. Pin the Rust binding family coherently; make clean baseline builds reproducible. This recommendation follows the supported integration options, not build-time measurements. [Build systems](https://kdab.github.io/cxx-qt/book/concepts/build_systems.html).
- Evaluate a native Kubuntu package first for Git-launched repository work; evaluate Flatpak if cross-distribution consistency matters more. A Kubuntu binary may depend on a newer glibc/C++ runtime than TUXEDO Legacy supplies despite matching Qt/KF. Confirm actual dependency versions and test each intended OS; a Flatpak also needs repository/temp-path and Git invocation validation. [Native deployment dependencies](https://doc.qt.io/qt-6.8/linux-deployment.html), [TUXEDO Legacy base](https://www.tuxedocomputers.com/en/What-the-future-holds-for-TUXEDO-OS-Ubuntu-and-Kubuntu.tuxedo), [sandbox access](https://docs.flatpak.org/en/latest/sandbox-permissions.html).

### Gaps

- No editor proof, benchmark, build, packaging trial or compatibility test was run. No speed or memory ranking is justified. No cancellation-latency promise is supported without choosing and measuring the algorithm.
- Actual word-diff/correspondence algorithm, text storage, encoding/newline policy, Git invocation/library route and recovery format are open. These affect the language boundary and the editor contract.
- KF6 binding availability does not certify KTextEditor's suitability for aligned blank space, gutters, wrapped mapping or shared decision undo. Public APIs and target versions need a focused evaluation.

## What is the Rust-first recommendation, and what would change it?

### Takeaway

Proceed toward a **Rust domain engine + CXX-Qt + Qt Quick/Kirigami** design, with an explicit editor feasibility gate on the Kubuntu baseline and permission for minimal C++ integration code. Keep an alternative **Rust engine + C++ Qt Widgets editor/frontend** available. AI maintenance and lack of prior Rust knowledge favor a small, explicit architecture; they do not establish that either route is effortless.

### Cited Findings

- CXX-Qt supplies Rust QObjects and Qt-thread queueing, while KDE documents their use with Kirigami. Together these support the proposed Rust-first route. [CXX-Qt](https://kdab.github.io/cxx-qt/book/), [KDE Rust route](https://develop.kde.org/docs/getting-started/rust/).
- QWidget editors and QML TextEdit expose different editor integration APIs. Selecting Rust does not decide between them. [QPlainTextEdit](https://doc.qt.io/qt-6.8/qplaintextedit.html), [QML TextEdit](https://doc.qt.io/qt-6.10/qml-qtquick-textedit.html).
- The Qt-independent core and separate desktop implementations follow this repository's stated portability convention. They are an architectural recommendation, not a commitment to ship another platform or reuse the UI. [Repository convention](../../.ai/kenkeep/nodes/practice-design-desktop-apps-around-screens-and-components.md).

### Inferences

Recommended provisional boundaries:

1. **Rust domain crate:** canonical session state, source identities, text/decision commands, undo/redo semantics, diff/correspondence inputs and results, recovery records, and explicit save/resolution outcomes. Exclude Qt object types from its public contracts. [Requirements](../../PRD.md), [explicit CXX boundary model](https://cxx.rs/).
2. **Rust Qt adapter:** CXX-Qt QObjects/models for file lists, revisions, choices and progress; GUI-thread notifications; cancellable job coordination. Keep business rules in the domain crate. [CXX-Qt generated QObject model](https://kdab.github.io/cxx-qt/book/), [threading contract](https://docs.rs/cxx-qt/0.10.0/cxx_qt/trait.Threading.html).
3. **Desktop UI:** QML/Kirigami for KDE presentation and controls, conditional on the merge editor gate. Add C++ only for unwrapped Qt/KF calls and narrowly scoped document/editor functions where that is simpler than maintaining a general Rust binding. [KDE documented route](https://develop.kde.org/docs/getting-started/rust/), [document bridge](https://doc.qt.io/qt-6.10/qquicktextdocument.html).
4. **Fallback:** keep the same Rust domain crate; let C++ own widget editor views and Qt/KF integration. Use plain CXX when C++ owns all QObject adapters, or retain CXX-Qt when Rust-owned Qt models already simplify that boundary. Do not force CXX-Qt into a plain engine interface solely for consistency. [CXX interop](https://cxx.rs/), [CXX-Qt purpose](https://kdab.github.io/cxx-qt/book/).

Criteria that would change the UI/integration recommendation:

- **Choose the widget frontend** if the required three-pane editor needs less custom rendering/input/history machinery with QPlainTextEdit/KTextEditor. Keep the Rust backend preference. [Widget APIs](https://api.kde.org/ktexteditor-view.html), [editor requirements](../../PRD.md).
- **Keep Qt Quick** if its editor evaluation demonstrates the required behaviors with public APIs and a maintainable document adapter. Do not choose it because a hello-world Rust/Kirigami tutorial exists. [TextEdit API](https://doc.qt.io/qt-6.10/qml-qtquick-textedit.html), [QQuickTextDocument](https://doc.qt.io/qt-6.10/qquicktextdocument.html).
- **Use Python only with a specific advantage**, such as a materially easier editor integration verified on the target distro. That would still require a decision about how Python and Rust share data and who owns history; it is not the default given the developer's preference. [PySide editor access](https://doc.qt.io/qtforpython-6.8/PySide6/QtWidgets/QPlainTextEdit.html).
- **Revisit the binding choice** if CXX-Qt cannot support the chosen editor/model contract on Qt 6.10.2, or if maintaining wrappers costs more than a C++ Qt adapter. Do not switch to qmetaobject solely to avoid seeing C++; its own scope and maintenance warning remain relevant. [CXX-Qt bridge design](https://kdab.github.io/cxx-qt/book/), [qmetaobject scope](https://github.com/woboq/qmetaobject-rs).
- **Revisit performance architecture after measurement**, including representative repeated passages, long lines, whitespace-only changes, large sessions and rapid edits. Decide acceptable input latency, cancellation response and memory bounds before claiming Rust, C++ or Python meets them. [PRD's unvalidated reading limits](../../PRD.md).

### Gaps

Questions to resolve before final stack selection:

- How much C++ glue is acceptable alongside Rust: unwrapped calls only, an editor component, or an entire widget frontend if that reduces total maintenance?
- Given AI-led maintenance, who will validate recovery and merge correctness, inspect failed builds and review generated unsafe/FFI code? Would a single command for build/test/package and an intentionally small binding contract make the workflow manageable?
- Is the target an unmodified Kubuntu 26.04 install, its normal updates, or also backports? Which architecture is required? Does the user's TUXEDO installation mean Legacy or the Debian-based line?
- Is first distribution a local native package, source build, Flatpak, or a broader distro release? Must the app use host Git/configuration, and where do repositories and launch-time temporary files live?
- What real file/session sizes, long-line lengths and input latency are acceptable? Must diff jobs interrupt immediately, or is bounded cooperative cancellation with stale-result rejection adequate?
- Which editor behaviors are decisive: wrapped alignment, source/result anchor stability after manual edits, IME, Unicode offset handling, whitespace indications, line controls and text-plus-decision undo? These are acceptance gates, not optional polish.

All remain open decisions. Research supports a Rust-first path with CXX-Qt and a deliberate editor fallback; it does not establish a completed stack choice.
