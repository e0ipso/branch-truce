# Let editor feasibility decide the frontend

**Recommend a Rust core with CXX-Qt and Qt Quick/Kirigami, conditional on an editor prototype.** Preserve Rust with thin C++ Widgets integration as the fallback if editor reuse proves easier to maintain. Confirmed constraints are native Linux/KDE, Rust preference, AI maintenance, Tuxedo OS use, and Kubuntu 26.04 LTS as the target baseline. The [PRD](../PRD.md) requires offline merge/rebase work, all current conflicts, editable results, separate Save and Mark resolved, and recovery. Git mergetool compatibility remains an intent alongside those requirements. This research memo proposes choices and unresolved gates; it approves no TechSpec or product-scope change.

## Qt Quick fits the shell; the editor decides

Qt is the application platform. QML describes interfaces; Qt Quick supplies visual items, input and rendering; Qt Quick Controls supplies controls. Kirigami adds higher-level KDE components. KDE HIG supplies interaction guidance, while Breeze supplies styling and visual assets, with Breeze Icons separate. KDE recommends Quick/Kirigami for new applications and recognizes Widgets for complex desktop interfaces. These are complementary roles, not competing toolkits. ([Qt overview](https://doc.qt.io/qt-6/topics-ui.html), [KDE guidance](https://develop.kde.org/hig/kde_app_design/), [HIG](https://develop.kde.org/hig/), [Breeze](https://raw.githubusercontent.com/KDE/breeze/Plasma/6.3/README.md))

**QML is the provisional shell choice, not a proven merge editor.** TextEdit provides editing foundations; KSyntaxHighlighting supplies QML syntax highlighting. Neither supplies three-way correspondence or decision history. KTextEditor offers QWidget views and richer editor APIs. QQuickWidget embeds Quick into Widgets, so it does not solve placing KTextEditor inside QML. ([TextEdit](https://doc.qt.io/qt-6.10/qml-qtquick-textedit.html), [syntax highlighting](https://api.kde.org/qml-org-kde-syntaxhighlighting-syntaxhighlighter.html), [KTextEditor](https://api.kde.org/ktexteditor-view.html), [embedding direction](https://doc.qt.io/qt-6.10/qquickwidget.html))

Prototype read-only sources around an editable center, optional base context, wrapped correspondence with unequal insertions, line/region actions, word highlighting, search, whitespace display, IME and Unicode offsets. Alignment must preserve copied/saved text. Prove one undo history for text and decisions, including Ignore without text changes. Neither candidate has demonstrated these requirements. If Widgets wins, retain Rust and thin C++ integration, while accepting that frontend code could be substantial.

## Rust fits the preference; explicit boundaries support maintenance

CXX-Qt generates Qt-facing Rust QObjects rather than wrapping every Qt/KDE API. KDE documents its Kirigami integration; missing integration can require C++. Keep session state, correspondence, decisions, history and recovery in ordinary Rust, behind value-based commands and results. Put QObject models and editor adaptation outside that core. ([CXX-Qt](https://kdab.github.io/cxx-qt/book/), [KDE Rust setup](https://develop.kde.org/docs/getting-started/kirigami/setup-rust/))

The backend alternatives are straightforward. C++ gives direct Qt/KF access and removes a language bridge, but departs from the Rust preference. Python/PySide6 exposes Widgets and Quick; KDE bindings cover only some Frameworks, so editor-specific coverage needs verification. Neither alternative has a measured maintenance or performance advantage here. AI maintenance favors a small contract, reproducible builds and explicit errors; it does not establish code correctness. ([PySide6](https://doc.qt.io/qtforpython-6.8/index.html), [KDE Python coverage](https://develop.kde.org/docs/getting-started/python/python-bindings/))

Let Qt own the event loop. Compute on immutable snapshots in Rust workers, reject stale results, and update Qt models on their owning thread. Use explicit FFI errors and lifetime rules. No general async runtime is selected. ([Qt model threading](https://doc.qt.io/qt-6.8/qabstractitemmodel.html#thread-safety), [CXX-Qt queueing](https://docs.rs/cxx-qt/0.10.0/cxx_qt/trait.Threading.html), [CXX errors](https://cxx.rs/binding/result.html))

## Distribution requires native dependencies and validation

Kubuntu 26.04 LTS supplies the verified release baseline **Qt 6.10.2, KF 6.24.0 and Plasma 6.6**. Start verification on 26.04.1 with normal updates. TUXEDO's announced matching Qt/KF versions establish neither compatibility nor incompatibility with the user's installation. Validate its actual distro base, glibc/C++ runtime ABI and package dependencies; the installed edition and versions remain unknown. ([Kubuntu release](https://kubuntu.org/news/kubuntu-26-04-release-notes/), [downloads](https://kubuntu.org/download/), [TUXEDO update](https://www.tuxedocomputers.com/en/TUXEDO-OS-receives-update-to-KDE-Plasma-6-6-x.tuxedo), [native deployment constraints](https://doc.qt.io/qt-6.8/linux-deployment.html))

The proposed build needs Rust/Cargo, the CXX-Qt crate family, a C++ compiler, Qt development libraries and QML tooling, plus CMake/ECM when using that integration. Runtime needs include Qt Core/Gui/Qml/Quick/QuickControls2, Kirigami, deployed QML modules, platform/style plugins and installed Git. Desktop styling adds QQC2 Desktop Style, Breeze/Plasma Integration and QApplication through Qt Widgets. SyntaxHighlighting is optional; the fallback adds Widgets/KTextEditor and their dependencies. Pin versions after a clean baseline build. ([CXX-Qt builds](https://kdab.github.io/cxx-qt/book/concepts/build_systems.html), [desktop style contract](https://raw.githubusercontent.com/KDE/qqc2-desktop-style/v6.19.0/README.md), [deployment](https://doc.qt.io/qt-6.8/linux-deployment.html))

A native `.deb` first is a proposal. Flatpak needs additional repository, worktree-metadata and helper access design; `flatpak-spawn --host` crosses into unsandboxed host execution. Verify Wayland, fractional scaling, accessibility and packaged plugins separately. ([Flatpak permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html), [host execution](https://docs.flatpak.org/en/latest/flatpak-command-reference.html#flatpak-spawn))

## Git CLI fits a narrow adapter, with unresolved launch ownership

Propose installed Git behind a Rust adapter using `std::process::Command`, executed off the GUI thread with asynchronous supervision as appropriate. QProcess is unnecessary. Native bindings remain alternatives: `git2` binds libgit2; pure-Rust `gix` exposes relevant plumbing, but either requires conversion/index-behavior validation against Git. ([git2](https://docs.rs/git2/latest/git2/), [gix](https://docs.rs/gix/latest/gix/))

Use NUL-delimited unmerged-index discovery and blob IDs for stable sources. Save writes only the result; Mark resolved saves, stages one exact literal path, then verifies index state while preserving unrelated entries. Keep unsupported files visible. Never commit or continue operations automatically. ([discovery](https://git-scm.com/docs/git-ls-files), [blob retrieval](https://git-scm.com/docs/git-cat-file), [staging](https://git-scm.com/docs/git-add))

Constrain subprocesses to a selected absolute Git executable, fixed subcommands/options, explicit cwd/environment, separate argv, literal pathspecs and `--`. Bound output and work, drain both streams, supervise cancellation and helpers, and inspect state after interrupted writes. Shell-free spawning is no sandbox. Disable discovery helpers, pagers, external diff/textconv and lazy fetching where supported. Staging can invoke clean/process filters and post-index-change hooks. Define trusted-repository/helper policy without silently disabling required conversions or weakening `safe.directory`. Host Git/helpers retain user privileges and can perform network I/O. ([Git controls](https://git-scm.com/docs/git), [configuration](https://git-scm.com/docs/git-config), [filters](https://git-scm.com/docs/gitattributes), [hooks](https://git-scm.com/docs/githooks))

**The launch protocol remains unresolved.** Conventional mergetool receives per-file inputs; successful exit can trigger parent staging, while failure can restore a backup over a saved draft. Detaching can report success prematurely. Git also loops over paths. Propose separate repository-session and compatibility entry points, preserving all-files work and mergetool intent. Prototype parent exit handling, staging acknowledgment, backup ownership, cancellation and multi-file coordination before claiming compatibility. `trustExitCode` alone cannot solve them. ([protocol](https://git-scm.com/docs/git-mergetool), [inspected v2.56.0 implementation](https://raw.githubusercontent.com/git/git/v2.56.0/git-mergetool.sh))

## Additional questions have provisional answers

Which encodings, EOLs and binaries? Preserve BOM, final newline and line endings; decode explicitly, reject unsupported conversions visibly, and keep binaries outstanding. Git attributes can distinguish stored bytes from worktree bytes. ([attributes](https://git-scm.com/docs/gitattributes))

Which file/session and line-length limits? Measure representative inputs before selecting budgets; reject excess explicitly rather than truncate work. Which recovery format? Persist app-owned source snapshots, edits, decisions, saved/reviewed revisions and pending mutations independently of temporary mergetool files; validate identity before restore.

How should worktrees and unusual paths behave? Discover actual Git/common directories; preserve byte paths internally and test non-UTF-8 display/Qt boundaries. Validate result containment and symlink races separately from argv safety. How should stale writes fail? Recheck worktree, operation, index and target baselines before mutations, verify afterward, and retain buffers on mismatch. These checks do not make save-plus-stage atomic or add reconciliation scope. ([locations](https://git-scm.com/docs/git-rev-parse), [path encoding](https://doc.qt.io/qt-6/qfile.html), [path races](https://docs.kernel.org/filesystems/path-lookup.html), [locking](https://raw.githubusercontent.com/git/git/v2.56.0/lockfile.h))

What remains portable? Keep Qt objects, editor offsets and process mechanisms outside domain contracts. A later edit needs renewed review even if Git still stages an earlier version. Editor feasibility, launch ownership and trust policy are the next decision gates. **No implementation, performance or compatibility tests were run.**
